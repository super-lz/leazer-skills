# 项目发现

目标是建立当前项目的品牌模型和适用性清单。发现结果决定后续检查项，不能预设 Flutter 项目一定使用 flavor、固定平台或固定外部服务。

## 1. 建立仓库上下文

先确认：

- 仓库根目录、当前分支、工作区状态和相关未提交改动；
- 当前作用域的协作规则；
- 产品主规格、品牌指南、构建说明和活动计划；
- 本次目标品牌和请求属于新增、编辑、停用、删除还是审计。

优先使用 `rg --files`、`rg` 和项目已有命令。避免通过全仓文件名猜测语义；命中后读取调用链和配置消费者。

## 2. 判断品牌模型

沿以下问题追踪真实实现：

1. 品牌目标在哪里登记或取得？
2. 目标在编译前、启动时还是运行期间选择？
3. Flutter 如何取得品牌文案、属性、资源和环境配置？
4. 原生平台如何取得应用身份、资源、签名和能力？
5. IDE、命令行、CI 和发布流程如何传递目标？
6. 未知、缺失或错配目标如何失败？
7. 最终产物如何验证目标身份和资源内容？

将结果分类为：

- 构建时品牌：每次构建确定一个品牌；常见信号包括 Dart define、flavor、Scheme、Configuration、product 或独立入口。
- 运行时品牌：同一产物可选择或切换品牌；关注持久化、缓存、状态刷新和权限边界。
- 远端配置品牌：服务端或部署配置决定品牌；关注启动失败、缓存版本、签名校验和离线行为。
- 混合模式：平台身份在构建时固定，部分展示或能力在运行时配置；分别记录两条链路。

## 3. 发现品牌数据源

搜索并确认消费者，而不是只记录文件：

- YAML、JSON、Dart 常量、ARB、本地化资源或远端配置；
- Flutter asset 声明、生成器及生成结果；
- Android product flavor、source set、manifest placeholder 和 Gradle property；
- iOS Scheme、Build Configuration、target、plist、entitlements 和 asset catalog；
- OHOS product、target、module、resource 和 signing configuration；
- Web、桌面或其他平台的身份、资源和打包入口；
- IDE 启动配置、构建脚本、CI 参数、产物上传和发布配置。

某个平台目录存在不等于项目正式支持该平台。以规格、可达构建入口和实际维护证据综合判断。

## 4. 发现条件能力

对每项能力检查规格、依赖、原生配置、初始化、业务入口、后台交互和验证资料：

| 能力类别 | 常见信号 | 还需确认 |
| --- | --- | --- |
| 本地化 | ARB、locale、平台本地化资源 | 品牌字段是否随语言一致刷新 |
| 地图与定位 | Flutter 插件、原生 SDK、定位权限、Key | 当前品牌是否启用及真实鉴权 |
| 推送 | SDK、注册初始化、原生配置、后台品牌标识 | 前后台收件、点击和解绑 |
| Deep Link | 路由解析、Scheme、App/Universal Link | 服务器关联文件及冷/热启动 |
| 第三方登录或分享 | SDK、回调 Activity/Scheme、平台 App ID | 包身份、签名和回调归属 |
| 支付 | 支付插件、商户配置、回调和订单链路 | 品牌主体、环境和真实结果 |
| 分析与监控 | SDK、项目 ID、初始化 | 数据是否进入正确品牌项目 |
| WebView 或桥接 | 域名、JS channel、路由 | 品牌页面、权限和回调 |
| 发布与升级 | 商店、OTA、上传和版本接口 | 产物、渠道、灰度和回滚 |

项目还可能有其他品牌相关能力。任何依赖品牌身份、配置、资源、后端标识或外部账号的能力都加入适用性清单。

## 5. 判定适用性

为每个领域记录：

```text
领域：
适用性：APPLICABLE / NOT_APPLICABLE / UNKNOWN
依据：
品牌相关边界：
需要的验证：
```

- `APPLICABLE`：规格要求或可达实现使用该能力。
- `NOT_APPLICABLE`：规格明确不需要，或代码与构建证据共同证明当前项目/品牌不包含该能力。
- `UNKNOWN`：证据冲突或不足；转为 `NOT_VERIFIED` 或 `REQUIRES_PRODUCT_DECISION`。

没有配置值不能单独证明不适用；它可能正是缺项。

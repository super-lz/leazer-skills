# 生命周期操作

## 共同入口

开始任何操作前：

1. 完成项目发现并确认品牌模式。
2. 明确最小完整用户结果、非目标和验证范围。
3. 对照项目规格判断是否引入或改变稳定语义。
4. 列出已确认信息与缺失决策，不把占位值当作正式配置。
5. 确认已有品牌和无关工作区改动需要保护。

## 新增品牌 `add`

### 输入

按项目适用范围收集，而不是要求固定表单：

- 稳定目标 ID、显示名称、法律主体和能力范围；
- 支持的平台及相应包身份；
- 品牌文案、语言、资源和环境配置；
- 目标选择、开发、构建、签名和发布方式；
- 适用外部服务的品牌账号、非敏感标识和凭据状态；
- Deep Link、域名、后台品牌枚举和兼容要求；
- 正式验收设备、环境、账号和渠道。

产品事实未确认时，先完成不依赖它们的分析或槽位设计；不得填入从旧品牌推导的正式值。

### 实施顺序

1. 同步已经确认的产品身份、能力和失败语义。
2. 沿当前品牌模式登记新目标和 Flutter 品牌数据。
3. 创建独立资源与环境槽位，并明确允许共享的内容。
4. 接入各适用平台的目标、身份、资源、签名接口和能力配置。
5. 接入 IDE、命令行、CI、产物命名、上传和发布归属。
6. 接入适用的后端品牌标识与外部服务。
7. 扩展项目已有校验和测试；不删除失败校验来容纳新目标。
8. 生成并验证新目标，回归已有目标，检查最终产物和适用真机路径。

### Manifest 加平台目标的项目

如果项目已使用品牌 YAML/JSON 等 manifest 与平台 flavor、Scheme、Configuration 或 product：

- 沿现有 manifest schema 补齐字段、语言和类型；
- 登记新目标并运行已有生成器；
- 保持 Flutter 品牌语义与平台原生身份分工；
- 扩展每个平台现有目标映射；
- 验证逻辑目标、Flutter 生成结果、平台目标和最终产物一致；
- 不默认让 manifest 生成包 ID、签名或原生能力，除非当前项目已正式这样设计。

## 编辑品牌 `edit`

先从变化语义决定传播范围：

| 修改类型 | 典型影响范围 |
| --- | --- |
| 文案或主体 | manifest、本地化、协议与展示；主体变化可能影响商店和支付 |
| 功能能力 | 入口、直接路由、后台任务、请求和失败行为 |
| 同路径资源 | 资源文件、缓存、最终产物和视觉验收 |
| 资源结构 | asset 声明、生成 API、所有品牌同构性和产物隔离 |
| 环境配置 | 配置消费者、环境差异和真实服务请求 |
| 平台包身份 | 原生工程、签名、商店、第三方平台和升级兼容 |
| Deep Link | Flutter 解析、各平台注册、服务器关联文件和真机唤起 |
| 外部服务 | SDK 配置、平台账号、后端标识和真实回执 |
| 构建发布 | IDE、CI、签名、产物路径、上传和通知 |

执行与影响范围成比例的验证。共享 schema、生成代码或构建入口变化时回归所有品牌；单品牌同路径资源替换不要求无关外部服务重新验收。

## 停用品牌 `deactivate`

先定义停用层级：隐藏业务入口、停止新构建、停止发布、停止后台服务或完全停止用户访问。分别检查：

- 已安装版本的行为和服务期限；
- 登录、推送、Deep Link、支付、升级和数据访问；
- CI、商店、OTA、下载入口和通知；
- 用户提示、恢复或迁移方式；
- 需要保留的签名、平台应用和历史配置。

停用完成不等于可以删除源码或外部平台配置。

## 删除品牌 `remove`

物理删除前需要可核实结论：

- 没有仍需支持的线上安装包或已有明确迁移方案；
- 后端品牌枚举、数据和接口已有处理决定；
- 推送、Deep Link、域名、商店、OTA 和第三方平台不再需要；
- 默认品牌、默认 product、兼容回退或工具链要求已迁移；
- 签名与发布历史按政策保留；
- 删除不会破坏共享 schema、生成器、已有品牌和构建入口。

任一必要结论缺失时，报告 `BLOCKED` 或 `REQUIRES_PRODUCT_DECISION`，并优先提出可逆的停用方案。

删除后运行目标集合、生成器、适用平台构建、已有品牌回归和全仓残留引用检查。

## 完整性审计 `audit`

默认只读：

1. 建立项目地图和适用性清单。
2. 追踪一个逻辑品牌从事实源到 Flutter、平台构建、产物和外部服务的完整链路。
3. 检查正向目标、错误目标、资源隔离和已有品牌回归证据。
4. 区分仓库当前事实、历史证据和当前未验证状态。
5. 按四层完成度报告，不为产生修改而修改项目。

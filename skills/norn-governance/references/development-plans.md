# 可续接开发计划

`norn-governance/plans/` 保存未完成开发的当前状态，使同一分支可以在另一会话或设备继续。计划只是临时导航，绝不是产品权威、实现事实、Git 历史或机器治理事务。

## 何时创建

至少满足一项条件时创建计划：

- 当前工作会话结束时，任务预计仍未完成；
- 用户准备在另一设备继续同一分支；
- 多个依赖检查点、迁移、外部批准或高成本验证使重建上下文明显有风险。

能在当前会话内低成本完成并验证的工作，不创建计划。

## 编写前调查

保存计划前：

1. 核对仓库身份、分支或 worktree、Git 状态和稳定基线；
2. 读取适用的 `AGENTS.md` 和完整主规格；
3. 检查相关入口、代码路径、符号、测试、配置、依赖和当前失败；
4. 把已验证事实与假设、仍需负责人的决策分开；
5. 把已接受结果转化为明确需求和可观察验收证据。

不要只是把用户原话扩写成通用阶段。如果实现位置尚不明确，增加有边界的发现步骤，写清搜索内容、范围以及结束发现所需的决策或产物。不得为了让计划显得完整而虚构路径或符号。

## 文件与必需内容

使用 `norn-governance/plans/YYYY-MM-DD-<task>.md`，每个活动任务一个文件。需求和步骤数量应按实际工作调整，不保留空占位项。

```markdown
# <任务>

- 状态：active | blocked
- 分支：<branch 或 worktree>
- 基线：<稳定分支或 revision>

## 结果与边界

- 结果：<可观察的完成结果>
- 完成条件：<用户或系统可见的验收证据>
- 非目标：<明确排除的范围>

## 已验证基线

- `<规格章节或 path#symbol>`：<已验证事实和证据>
- 假设：<尚不能视为事实的假设>
- 未知项：<未决事实及其对计划的影响>

## 需求

### R1 — <明确行为或约束>

- 来源：<主规格章节、已确认需求或必须保留的代码/测试不变量>
- 验收：<可测试或可审查证据>
- 规格回写：none | <所需规格章节和步骤>

## 实施步骤

### S1 [pending] — <具体中间结果>

- 需求：R1
- 目标：`<repository-relative path#stable-symbol>`
- 变化：<具体行为或契约变化>
- 依赖：none | S<n> | <外部条件>
- 风险或边界：<仅记录实质情况>
- 验证：`<命令、测试或检查>` → <预期证据>

## 续接检查点

- 已完成：<已完成步骤 ID 和验证结果>
- 进行中：none | <唯一的步骤 ID 和当前状态>
- 下一步：<包含路径、符号、命令或决策的单一精确动作>
- 阻塞或决策：<负责人、条件和恢复触发器>
- 已完成验证：<命令或证据及结果>
- 待验证：<与需求或步骤对应的剩余证据>
```

## 步骤质量规则

- 只使用 `pending`、`in_progress` 和 `completed`；最多一个步骤处于 `in_progress`。
- 每个实施步骤至少关联一项需求，并标明仓库相对目标或稳定符号。
- “变化”描述行为或契约差异，而不是编辑动作。
- “验证”写明能推翻完成结论的命令、测试、检查或可观察结果。
- 发现步骤写明搜索范围和必须产出的具体决策或证据，不能假装实现位置已经明确。
- 改变持久产品语义的需求必须在同一变更中写入主规格。计划只引用该工作，不能成为权威。
- 只保留能降低实施、审查或续接成本的细节，不把计划写成设计论文或聊天记录。

以下表述单独出现时无效：

```markdown
- 实现功能。
- 增加测试。
- 更新文档。
- 继续处理剩余工作。
```

有效步骤必须写明需求、目标、预期变化、依赖和验证。例如：

```markdown
### S2 [pending] — 在分析阶段拒绝无效目标父路径

- 需求：R2
- 目标：`skills/norn-governance/scripts/norn_governance/analyzer.py#_transaction_output`
- 变化：目标父路径是普通文件时，在 apply 前报告阻断冲突
- 依赖：S1 路径枚举
- 风险或边界：嵌套目标，以及分析后被替换的父路径
- 验证：`python3 -m unittest discover -s skills/norn-governance/tests -p 'test_analyzer.py' -v` → 目标冲突用例通过且仓库未被写入
```

## 检查点与续接

- 在有意义的实施或验证检查点、预期中断前，以及阻塞状态变化时更新计划。
- 续接时先核对仓库身份、分支、Git 状态、主规格、相关代码和外部状态，再把计划与当前事实比较。
- 事实变化时更新或丢弃过期计划。不得用计划覆盖主规格或当前代码。
- 计划中的既有决策只是上下文，不是破坏性操作、外部操作或扩大范围的新授权。
- 同时更新步骤状态和续接检查点。没有对应证据时，不得声称步骤已完成。

## Git 与清理

计划可以随开发分支移动，使另一设备继续工作，但只有用户授权相应 Git 操作时才能提交或推送。不要创建计划索引、已完成计划归档、全局 current plan、README 或占位文件。

任务完成或取消时，先把持久结果写入主规格、代码、测试或 Git 历史，再删除计划。受阻计划只有在写明解除阻塞条件和精确的第一个恢复动作时才可保留。

# Norn Governance

建立清晰的项目事实模型：主规格保存稳定语义，代码和 Git 保存实现现实与演化，`plans/` 保存未完成开发的可续接状态，`appendix/` 只保存必要证据和辅助理解。

## 语言与接口

- 当前面向开发者或代理阅读的规则、提示、报告和错误信息使用中文优先；产品名、路径、命令参数和必要技术术语可保留英文。
- `analyze | resolve | apply`、CLI 参数、JSON key、枚举值、状态值和 managed block ID 是稳定机器接口，保持英文。
- JSON 中的 `reason`、`evidence`、`risk`、`verification`、告警和验证范围说明是人读展示值，使用中文；自动化不得依赖这些自然语言值判断。
- 升级只替换受管区块，不翻译或覆盖项目自有主规格和区块外定制。历史模板与测试 fixture 保持原始字节。

## 先判断任务类型

- **初始化**：项目没有 Norn 或旧 Norn 结构。
- **结构迁移**：把可确认的旧 Norn 固定治理文件迁移到当前路径。
- **升级**：更新 Norn 受管规则，保留项目规格与区块外定制。
- **文档归位审计**：用户要求迁移、合并、删除或“全部切到 Norn”的项目文档。此模式必须按内容职责审计，不能按旧目录或文件名机械移动。

结构迁移可以与文档归位审计发生在同一任务中，但必须分别展示语义判断与机器事务。

## 内容职责

对每份受影响文档判断其真实职责：

- 当前稳定目标、流程、边界、契约、失败行为或验收标准 → 合并进 `norn-governance/spec/main-spec.md`，必要时按稳定系统边界拆分子规格。
- 开发中尚未完成、需要在另一会话或设备继续的状态 → `norn-governance/plans/YYYY-MM-DD-<task>.md`。
- 历史理由、原始证据或辅助理解材料 → `norn-governance/appendix/`。
- 当前实现机制 → 代码、测试或必要注释；重复文档删除。
- 仍有独立用户用途的普通项目文档 → 保持在最合适的项目位置；采用 Norn 不等于把所有 Markdown 搬进治理目录。

一个文件混合多种职责时，先把稳定语义收敛到主规格，再决定保留证据、移动活动状态或删除重复内容。Appendix 中独占的当前规范意味着迁移尚未完成。

## 主规格同步提示

- 发现新的或变更的稳定需求，且尚需开发者确认才能回写和实施时，用独立提示块说明。提示块首行以 `🚨` 开头，逐条列出拟写入主规格的语义变化，并明确询问开发者确认还是调整。若开发者已在当前上下文明确确认相同变化，不得仅为满足格式重复询问。
- 当前有效代码和测试已经证明稳定行为、主规格只是遗漏，且主规格编辑属于开发者已授权的变更范围时，在同一变更中自动同步。只有主规格已实际修改后，才用首行以 `⚠️` 开头的独立提示块，逐条列出真正完成的语义回写。
- 没有待确认或已完成的规格回写内容时，不显示提示块，不输出 `🔵`、“无需回写”、“未发现变化”等占位状态。主规格内容没有真正修改时，禁止声称“已同步主规格”或使用等价措辞。

提示块可按用户语言组织，但保持以下语义和醒目程度：

```markdown
🚨 发现需要确认的主规格变化：

1. <稳定需求或约束>
2. <验收或失败语义>

请确认：按以上内容回写并实施，还是先调整？
```

```markdown
⚠️ 已同步主规格：

1. <实际回写内容>
2. <对应稳定行为>
```

这些提示只改变重要规格动作的呈现，不改变确认边界、自动回写条件或治理事务的授权要求。

## 安全治理事务

1. 确认目标仓库、Git 状态和用户意图；读取目标仓库 `AGENTS.md`、主规格及任务要求的材料。
2. 内部运行 `scripts/manage_norn_governance.py analyze --target <repo> --report-json`。输出的临时 `transaction.json` 是带指纹的**治理事务**，不是项目开发计划，也不进入仓库。
   - 默认只处理四个可确认的旧 Norn 核心文件。
   - 用户明确要求递归处理旧 `docs/spec/**`、`docs/appendix/**` 或两者时，才加入对应范围，并逐文件展示。
3. 核实报告中的归属证据、结构状态、语义审计提示、写入、移动、删除、风险和验证边界。`current` 只表示受管结构当前，不证明主规格语义完整。
4. 若涉及项目文档归位，完整阅读范围内文件，先给出逐文件处置表和主规格回写摘要。不能把“全部迁移”解释为“全部放进 appendix”。
5. 对无歧义的完整动作摘要取得确认。归属不明、删除、受管区块修改或语义取舍必须显式列出。
6. 对受管冲突只使用报告允许的 `keep-current`、`adopt-template` 或 `semantic-merge`。语义融合产物必须在事务临时目录生成并绑定 SHA-256。
7. 内部通过 `resolve` 绑定冲突选择；执行前确认事务无冲突、目标与指纹未变化、用户确认仍对应当前摘要。
8. 内部运行 `apply`。项目文档的已确认语义归位作为同一任务中的普通仓库编辑执行，但不得伪装成机器事务已验证的内容。
9. 验证受管结构、manifest、单一主规格路径、Git 差异和内容职责：正常开发只读根规则与主规格必须足够；appendix 不得独占当前规范；plans 只包含活动未完成任务。

目标、文件或事务指纹变化后必须重新分析并重新确认。未经明确要求，不提交、不推送、不创建分支、不修改 Git 配置。

## 开发计划

`norn-governance/plans/` 是项目开发中的短期续接状态，不是治理机器事务。当前治理任务本身预计跨会话、跨设备或含多个依赖检查点时，先检查相关规格、代码、测试和 Git 状态，再读取并遵循 [references/development-plans.md](references/development-plans.md)。不得只把用户请求或聊天摘要填进模板；保存前必须把需求变成有来源和验收证据的明确条目，把实现变成关联具体目标与验证的有序步骤，并消除“实现功能”“补充测试”“继续处理”一类无法直接执行的描述。简单单会话任务不创建计划；完成或取消后删除计划。

## 边界

- 确定性脚本只管理固定 Norn 路径和用户明确授权的旧 `docs/spec/**`、`docs/appendix/**`；不猜测任意 Markdown 的语义。
- 完整项目文档重组必须由 Skill 做内容审计、展示处置并取得确认；路径不是内容职责证据。
- `main-spec.md` 初始化后归项目所有，升级不得用模板覆盖。
- 普通文件移动保持原始字节；目标碰撞、异常父路径、符号链接和特殊文件阻断执行。
- 源文件只有在目标校验成功后才能删除；旧目录只在完全为空时删除。
- 结构验证不能被表述为产品语义验证、代码验证或文档归位完成。

# 项目总指挥

本文件是本仓库的固定执行入口。每次执行任何操作前，先读根目录 `AGENTS.md`；是否继续读取其他文档，由当前任务、改动风险和开发者判断决定。

## 第一性原则

- 先确认真实文件、代码、运行状态和实现依据，再做结论。
- 不凭猜测改代码，不用辅助材料覆盖主实现规格。
- 当前实现必须能回到主实现规格中的目标、规则、边界或验收点。
- 一切判断先回到最终目的：真实用户是谁、真实问题是什么、用户要得到什么可感知结果、怎样验证结果已经达成。
- 任何新增功能、组件、状态、依赖、文档或流程，都应能说明它服务哪个真实需求；说不清用途时，优先不新增。
- 如果开发者提出的方向开始偏离最终目的、扩大范围、增加无关复杂度或削弱用户真实需求，先适当提示风险，再给出更贴近目标的最小方案。
- 项目长期可信来源只有三类：主实现规格是骨骼，定义业务语义、目标、流程、边界和验收；代码是皮肤和血肉，承载真实实现机制、当前可观察行为和可追溯代码事实；Git 历史记录演化轨迹、变更原因和变更范围。
- 主实现规格必须足够完整：即使脱离当前代码，也应能据此重建一个业务语义等价的系统；完整指目标、流程、边界、规则、状态变化、失败处理和关键不变量完整，不代表复述代码组织和实现机制。

## 工程哲学

这些原则是判断方式，不是机械清单。它们用于帮助 agent 在复杂项目里做取舍，而不是引入固定表格、重型流程或与当前目标无关的知识负担。

- 目的优先：先理解最终用户结果，再选择功能、技术和文档形态。
- 边界隐藏变化：好的模块和文档边界应隔离容易变化的决策，对外暴露稳定而少量的承诺。
- 近可分解：系统可以变大，但应尽量让局部变化不迫使全局理解和全局修改。
- 本质复杂度不可消灭，偶然复杂度应持续压低；不要用抽象、流程或文档制造新的理解成本。
- 从可工作的简单系统演化，不预设庞大结构；结构应随真实需求和稳定变化点长出来。
- 代码和规格要彼此照亮：规格说明为什么、承诺什么结果、遵守什么边界；代码说明真实怎样发生。
- 可观察行为会形成事实契约；对用户已经依赖的行为，修改前先确认影响。
- 熵会自然增长；每次新增都应伴随合并、删除或压缩的意识。

## 规格与代码分工

信息源要少。主实现规格不是代码复述，也不是 UI、接口、数据或流程的实现手册。它记录代码难以稳定表达、但决定业务语义等价性的内容：目的、流程串联、可用边界、状态变化、数据含义、权限边界、业务规则、跨边界承诺、失败处理、关键不变量和验收方式。

代码记录实现该语义的真实路径：呈现方式、交互机制、协议适配、数据访问、任务调度、函数拆分、模块复用、状态变量、框架 API、文件组织、性能技巧和其他实现机制。除非这些内容本身构成用户承诺、业务约束、跨系统契约或验收条件，否则不写入主实现规格。

判断是否写入主实现规格时，不看它属于哪类技术对象，只问一个问题：如果换一种语言、框架或代码结构重建系统，这个信息是否仍然必须保持，才能让用户得到相同业务流程、结果和边界？如果是，写入规格；如果只是当前代码如何做到，留在代码里。

## 目录入口

- `docs/AGENTS.md`：文档区入口，规定文档分类和治理规则。
- `docs/spec/AGENTS.md`：实现规格目录入口，规定主实现规格和未来拆分条件。
- `docs/appendix/README.md`：附录材料说明，面向读者理解，不影响实现优先级。

## 执行流程

1. 先读本文件。
2. 判断当前项目状态：
   - 空项目或缺少主实现规格时，先与开发者澄清目标、边界、核心流程和验收标准，形成或补齐主实现规格；未确认前不进入代码实现。
   - 已有实现时，先读代码现状和相关规格；若发现实现需要改变规格，或规格与代码现实冲突，按“实现规格回写规则”处理。
3. 根据当前任务判断是否需要读取主实现规格或未来新增的必要调研文档。
4. 读取代码、修改代码或验收结果时，主动识别主实现规格是否缺少当前稳定行为；发现回写候选就按“实现规格回写规则”处理。
5. 开发前在当前任务上下文里列清目标和方案，按步骤实现。
6. 实现前做第一性原理思考：确认本次改动服务的用户结果、最小必要范围、验收方式和明确不做的内容。
7. 实现时优先保持最小闭环，避免引入与当前目标无关的抽象、状态、依赖、文档和流程。
8. 继续开发时，以代码现状、测试结果和主实现规格为依据，不依赖临时执行记录。

## 第一性原理思考

执行任何非平凡改动前，用以下问题压缩范围；不需要机械逐项回答，但结论应经得起这些问题追问：

- 最终目的：这个改动帮助哪个用户在什么场景下得到什么结果？
- 必要性：如果不做它，当前目标会失败吗？如果不会失败，优先不做。
- 最小性：有没有更小的实现能满足同一验收结果？
- 可验证性：这个结果能被测试、运行、手工验收或代码审查确认吗？
- 抽象价值：新增抽象、组件、状态或依赖是否隐藏了变化、降低了理解成本，还是只移动了复杂度？
- 可删除性：如果某段代码、文档或流程不能证明用途，应删除、合并或不新增。

如果开发者要求偏离第一性原理，应先给出简短提示；提示应服务决策，不应变成争论或阻断明确选择：

```text
这个方向可能偏离当前最终目的：<原因>。
更小的方案是：<建议>。
请确认是坚持扩大范围，还是按最小方案推进？
```

## 长期依据

项目长期依据只保留三类：

- 实现规格：业务语义源，承接产品目标和已确认的实现决策，说明目标、流程、边界、规则和验收标准。
- 代码本身：实现事实源，说明行为实际上如何发生，类型、模块边界、测试和必要注释承担主要技术说明。
- Git 历史：变更追溯源，追溯为什么发生变动、何时发生变动和变动范围，不替代规格或代码定义当前语义。

AI 对话和临时计划只用于形成当次决策，不作为长期依据；稳定决策必须进入实现规格或代码，真实变动必须能从 git 历史追溯。

## 实现规格维护

- `docs/spec/main-spec.md` 是默认主实现规格。落地到具体项目时，可以重命名为更明确的业务规格文件。
- 空项目先确定主实现规格，再开始开发；不能用未确认的猜测直接生成实现。
- 不主动频繁修改主实现规格。
- 后续出现新需求、新约束，或发现实现规格与代码现实冲突时，先总结需要改动的点并反问确认，再修改实现规格。
- 非空项目允许由代码现状反推规格更新需求；确认后的稳定决策必须回写主实现规格。
- 若要表达阶段边界，优先在主实现规格中增加简短的阶段边界和验收点，不新增开发日志文档。
- 主实现规格只记录稳定依据：目标、原则、组件边界、流程、接口、失败处理、关键决策、开放问题、阶段边界，以及决定业务语义等价性的规则、承诺和关键不变量。

## 实现规格回写规则

当代码和主实现规格不一致时，先判断差异属于哪一类：

- 确定的文档落后：如果非常确定当前变更在此前已经存在相关逻辑，代码中的行为是当前有效实现，并且主实现规格只是落后，必须自动更新主实现规格，不再额外询问开发者。
- 不确定的实现变更：如果代码里确实存在相关实现，但无法确定它是否应成为长期规格，例如可能是临时实验、局部兼容、未完成路径、隐藏开关或与既有目标冲突，不能直接回写；必须主动询问开发者确认。
- 无真实实现变动：如果检查后没有发现真实代码行为变化、稳定实现缺口或规格落后问题，不修改主实现规格；回复中用蓝色 emoji `🔵` 说明没有回写内容和原因。
- 新需求或新约束：如果当前任务引入新的目标、边界、流程、接口、验收标准或失败处理，先总结拟变更点并反问确认，再修改主实现规格。

判断“确定的文档落后”必须同时满足：

- 代码证据清楚：相关逻辑位于当前有效路径，不是死代码、注释、临时分支或未接入模块。
- 行为证据清楚：可以从代码、测试、运行结果或既有调用关系确认真实行为。
- 规格影响清楚：该行为会影响目标、组件边界、核心流程、接口、失败处理、验收标准、关键决策或非目标。
- 冲突风险清楚：没有发现同一规格点存在互相矛盾的实现、明显未完成状态或需要产品取舍的问题。

自动回写主实现规格后，回复中必须用分割线把回写提示和正常回答隔开，并用 `⚠️` 逐条列出回写内容：

```text
---
⚠️ 已自动回写到主实现规格：
⚠️ 1. <回写点>
⚠️ 2. <回写点>
```

需要开发者确认时，回复中必须用分割线把确认提示和正常回答隔开，并用红色警告 emoji `🚨` 逐条列出待确认项，明确询问“确认回写，还是修改后再回写”：

```text
---
🚨 发现可能需要回写主实现规格，但需要开发者确认：
🚨 1. <待确认点>
🚨 2. <待确认点>

请确认：直接回写，还是你修改后我再回写？
```

没有真实实现变动或没有规格回写依据时，回复中必须用分割线把检查说明和正常回答隔开，并用蓝色 emoji `🔵` 说明不回写原因：

```text
---
🔵 未发现需要回写主实现规格的真实实现变动：
🔵 1. <没有回写的原因>
```

## 文档治理

- 不记录开发过程、临时计划、每日进度和流水账。
- 代码本身是主要技术实现文档；技术细节优先沉淀到代码结构、类型、测试和必要注释中。
- 只有遇到必要且复杂的技术调研，才新增短文档；调研结论最终必须回填到主实现规格或代码。

# 实现规格目录入口

本目录保存权威实现规格。默认主实现规格是 `main-spec.md`；落地到具体项目时，可以重命名为更明确的业务规格文件。

## 当前规则

- 主实现规格是当前项目的最高实现依据。
- 主实现规格是项目骨骼，负责完整描述业务语义、目标、流程、边界、接口、失败处理和验收标准；代码是皮肤和血肉，负责承载真实实现机制、当前可观察行为和可追溯代码事实。
- 主实现规格必须能独立指导重建业务语义等价的系统；即使代码语言、框架和代码组织不同，依据本规格实现出的系统也应具备相同目的、流程、边界、状态变化、失败处理和关键不变量。
- 主实现规格必须以最终目的为中心：真实用户、真实问题、可感知结果和验收方式优先于功能堆叠。
- 本目录规则提供方法论而非重型流程。拆分、回写和抽象判断应追求清晰、定位效率和低认知负担，不为套用概念而新增文档结构。
- 空项目或缺少主实现规格时，先与开发者确认目标、边界、核心流程和验收标准，补齐主实现规格后再开发。
- 开发实现、测试和验收应回到主实现规格中的目标、规则、边界或验收点。
- 每个目标、流程、组件、接口、失败处理和验收点，都应能说明服务哪个真实用户需求；不能说明用途的内容不写入主实现规格。
- 读代码、改代码和验收结果时，都要主动识别主实现规格是否缺少当前稳定行为；不能只在开发者显式要求更新文档时才检查。
- 不主动频繁修改主实现规格，但不能让主实现规格长期落后于稳定代码现实。
- 如果非常确定代码中已经存在稳定有效逻辑，而主实现规格只是落后，必须自动回写主实现规格；回复时在分割线后用 `⚠️` 逐条列出已回写内容。
- 如果代码里确实存在相关实现，但无法确定是否应成为长期规格，必须先用红色警告 emoji `🚨` 逐条列出待确认项，询问开发者确认回写或等待其修改后再回写。
- 如果没有发现真实代码行为变化、稳定实现缺口或规格落后问题，不修改主实现规格；回复时在分割线后用蓝色 emoji `🔵` 说明没有回写内容和原因。
- 出现新需求、新约束，或发现实现需要改变规格时，先总结改动点并反问确认，再修改。
- 不在本目录记录开发流水、临时计划或阶段执行过程。

## 回写判断

允许自动回写的情况必须同时满足：

- 相关逻辑位于当前有效路径，不是死代码、注释、临时分支或未接入模块。
- 可以从代码、测试、运行结果或既有调用关系确认真实行为。
- 该行为会影响目标、组件边界、核心流程、接口、失败处理、验收标准、关键决策或非目标。
- 没有发现同一规格点存在互相矛盾的实现、明显未完成状态或需要产品取舍的问题。

自动回写后，回复格式固定为：

```text
---
⚠️ 已自动回写到主实现规格：
⚠️ 1. <回写点>
⚠️ 2. <回写点>
```

需要确认时，回复格式固定为：

```text
---
🚨 发现可能需要回写主实现规格，但需要开发者确认：
🚨 1. <待确认点>
🚨 2. <待确认点>

请确认：直接回写，还是你修改后我再回写？
```

没有真实实现变动时，回复格式固定为：

```text
---
🔵 未发现需要回写主实现规格的真实实现变动：
🔵 1. <没有回写的原因>
```

## 规格裁剪

维护主实现规格时，避免把愿望清单、临时想法和无关技术偏好写成长期依据。新增内容前用以下问题帮助判断，不把它们当作必须填写的模板：

- 是否直接服务当前最终目的和真实用户需求。
- 是否会影响业务语义、流程、边界、接口、状态变化、失败处理、验收标准、关键不变量或关键决策。
- 是否足够稳定，能约束后续实现，而不是一次性执行记录。
- 是否能帮助重建业务语义等价系统；如果不能，就不进入主实现规格。

主实现规格不按 UI、接口、数据、任务、权限或集成类型来决定是否写入，而按业务语义等价性来决定。普通实现机制留在代码里，例如呈现方式、交互机制、协议适配、数据访问方式、任务调度方式、函数拆分、模块复用、状态变量、框架 API、文件组织或内部性能技巧。只有当这些内容本身成为用户承诺、业务约束、跨系统契约或验收条件时，才提升为规格内容。

## 拆分规则

当前先保持单一主实现规格，不拆分。

只有出现以下情况之一，才考虑把主实现规格升级为目录化规格：

- 主规格过长，阅读一个改动点必须扫大量无关章节。
- 若干部分已经形成稳定独立系统边界。
- 不同章节变化频率明显不同，单文件维护开始互相干扰。
- 多次出现代码实现无法清晰对应到规格章节。
- 人或 agent 经常误读主次关系。

拆分时优先按系统边界拆，不按开发阶段拆。推荐形态是：

```text
docs/spec/<feature-or-system>/
  index.md
  <subsystem-a>.md
  <subsystem-b>.md
  <subsystem-c>.md
```

`index.md` 保留目标、原则、关键决策和文档地图；子文档承载各自稳定系统边界。

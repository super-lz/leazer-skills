# Norn 治理目录

本目录分离持久语义、活动开发状态和可选证据，使每类内容只在能回答当前问题时加载。

## 目录职责

- `spec/`：主规格；只有当规模确有需要时，才包含由 `main-spec.md` 索引的子规格。这是项目的语义权威。
- `plans/`：每个活动且未完成的开发任务一个文件。计划让分支工作可跨会话或设备续接，但不是规格或历史。
- `appendix/`：非规范证据和辅助说明。它是可选阅读材料，不能授权实现。

## 活动开发计划

- 当工作预计无法在当前会话或设备内完成，或多个依赖检查点使重建上下文明显昂贵或有风险时，创建计划。
- 文件名使用稳定日期和任务标识：`YYYY-MM-DD-<task>.md`。
- 编写前检查相关规格、代码、测试和 Git 状态。把已验证事实与假设、未决决策分开记录；计划不能代替调查。
- 定义可观察结果、带权威或确认来源及验收证据的明确编号需求、非目标和已验证基线。
- 使用有序的 `pending`、`in_progress` 或 `completed` 步骤。每个实施步骤都要写明满足的需求、仓库相对文件或稳定符号、预期行为变化、依赖或实质风险及其验证方式。目标未知时，使用包含具体搜索范围和预期决策的发现步骤，不得虚构路径。
- 最多允许一个 `in_progress` 步骤，并保留一个精确的下一步。“实现功能”“增加测试”“更新文档”等表述若没有目标、行为和验证，就不可执行。
- 使用仓库相对路径和稳定标识。不得存储密钥、文件正文、临时机器路径、命令过程记录或可复用批准。
- 续接时先核对仓库和规格，再信任计划。事实变化后，计划只是过期导航，不是权威。
- 仅在有意义的检查点更新计划。只有用户授权相应 Git 操作时，才随开发分支提交或推送计划。
- 任务完成或取消后，在持久结果进入规格、代码、测试和 Git 历史后删除计划。只有写明解除阻塞条件和第一个恢复动作时，才保留受阻计划。
- 不创建计划索引、已完成计划归档、全局 `current-plan.md`、README 或占位文件。没有活动任务时，目录可以不存在。

## 附录（appendix）纪律

- 只保留追溯理由时有价值且重建成本过高或不合适的证据与说明。
- 每个 appendix 文件都必须声明其非权威性质，并指出它帮助解释的当前规格边界。
- appendix 中出现当前规范规则时，把规则提升到主规格，仅保留历史证据。
- 对重复、过时或无人负责的文档，优先删除而不是保留。

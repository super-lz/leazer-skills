# Norn 协作约定

Norn 让项目事实保持精简、明确且可续接。持久事实以仓库为准，不以聊天历史为准。

## 权威模型

不同问题分别使用以下事实来源：

1. `norn-governance/spec/main-spec.md` 是主规格，保存持久的产品目的、用户结果、规则、边界、契约、失败行为和验收条件。
2. 当前可达代码和测试是实现现实，说明已接受规格目前如何工作。
3. Git 历史记录演进，说明规格与实现何时以及为何变化。

`norn-governance/plans/` 是临时开发状态，不是权威。`norn-governance/appendix/` 是可选证据和说明材料，也不是权威。二者都不能静默覆盖主规格或当前实现事实。

## 必须阅读

- 开始非简单工作前，读取本文件。
- 提出架构方案、改变行为或实施新需求前，完整读取主规格。
- 续接未完成工作时，先核对分支、Git 状态、主规格和相关代码，再只读取匹配的活动计划。
- 仅当任务需要原始证据、历史理由或辅助说明时读取 appendix。

## 开发生命周期

1. 明确真实用户结果、最小完整边界、非目标和验证方式。
2. 对照主规格和当前代码核对请求。新的或变更的持久需求必须先摘要并获得确认，才能修改规格或开始实施。
3. 仅当任务预计跨会话或设备，或多个依赖检查点使可靠续接明显更有价值时，创建活动开发计划。保存前检查相关规格、代码、测试和 Git 状态；记录可观察结果、明确需求与非目标、已验证基线，以及关联仓库相对目标和验证方式的有序步骤。未知位置应成为有边界的发现步骤，不能虚构路径。简单工作保留在当前任务上下文中。
4. 按主规格实施，用代码和测试保存实现事实。没有当前可测需求时，不新增基础设施或抽象。
5. 在有意义的检查点更新活动计划。保持步骤状态准确，最多一个步骤处于 `in_progress`，保存验证证据、阻塞项和一个精确的下一步。不要把计划写成过程记录。
6. 完成前执行与风险相称的验证，并核对稳定行为与主规格一致。
7. 任务完成或取消后，把持久结论移入规格、代码、测试或 Git 历史，并删除活动计划。受阻计划只有在写明具体恢复条件时才可保留。

## 主规格同步

- 新的或变更的持久需求必须先摘要并获得确认，才能修改规格或实施。仍需确认时，用独立提示块说明，首行以 `🚨` 开头，逐条列出拟写入主规格的精确语义变化，并询问开发者确认还是调整。若开发者已在当前上下文明确确认相同变化，不得仅为满足格式重复询问。
- 当前可达代码和测试已经证明某项稳定行为、主规格只是遗漏，且规格编辑属于开发者授权范围时，应在同一变更中同步主规格。只有主规格已实际修改后，才使用首行以 `⚠️` 开头的独立提示块，并且只列出真正完成的语义回写。
- 主规格内容没有实际变化时，禁止声称已经同步。没有待确认或已完成的规格回写内容时，完全省略提示；不得输出 `🔵`、“无需回写”、“未发现变化”或其他占位状态。
- 代码与规格冲突且意图无法证明时，停止并请求产品决策；不得为方便而选择任一事实来源。
- 不影响语义等价性的实现机制留在代码中。只有当它成为用户承诺、跨边界契约、安全规则或验收条件时，才提升到规格。
- 延后想法和 appendix 内容不能授权脚手架或实现；它们必须先进入已接受的当前规格范围。

## 文档归位

- `spec/`：重建语义等价系统所需的持久规范语义。
- `plans/`：活动且未完成的开发状态。
- `appendix/`：仅在追溯原因时使用的非规范证据或说明。
- 代码、测试和必要注释：当前实现机制与不变量。

按内容而不是文件名分类文档。一个文档混合多种职责时，应拆分或收敛，使每项持久陈述只有一个权威位置。

## 安全与验证

- 编辑前检查工作树，保留无关的用户修改。
- 不得提交密钥、真实个人数据、凭证、生产数据集或私有原始文档。
- 按变更风险考虑失败、取消、跨平台、安全、隐私、迁移和恢复影响。
- 只报告实际执行过的验证。Norn 结构处于 `current`，不代表项目语义完整或内容归类正确。

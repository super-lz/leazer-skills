# UI 清晰度审查

## 目标

从第一性原理判断每个界面元素是否必要。一个元素至少应帮助用户完成一件事：判断状态、作出选择、执行动作或从失败中恢复；否则优先删除。

简洁不是追求删除数量。不得为了少字而隐藏关键语义、安全边界、错误恢复或无障碍信息。

## 工作方式

1. 先查看真实界面、关联状态和产品规格，区分视觉表现、交互语义与内部实现。
2. 修改前列出候选项，按“删除、缩短、保留”分类，并用一句话说明理由。用户已明确要求实施时，列出后可在同一轮继续；如果修改会改变产品语义，先请求产品决策。
3. 对每个元素依次判断：
   - 同一事实是否已由图片、选中态、控件或附近区域表达？
   - 用户是否需要这条信息才能决定下一步？
   - 它是否只是在解释系统、设计理由或内部机制？
   - 同一状态、数值或进度是否在页面中重复出现？
   - 删除后是否会损害错误恢复、安全或无障碍理解？
4. 只做授权范围内的最小修改，不用新的解释替换刚删除的解释，也不凭空增加功能。
5. 修改后逐个检查受影响状态，确认层级、留白、文案和操作仍然无歧义；有画布或可运行界面时进行截图或实际交互验证。

## 判断规则

优先删除：

- 页面内容已经表达的标题、副标题或自我介绍。
- 与图片效果、选中按钮或控件状态同义的标签。
- 重复出现的百分比、进度、数量或复合状态。
- 用户无法据此采取行动的内部机制、协议细节或设计保证。
- 用户可以直接从当前列表或画面得出的统计。

优先缩短：

- 同时描述多个已知事实的复合状态，只保留当前界面无法表达的部分。
- 有价值但过度解释的标签，改为直接的对象名、动作名或结果名。

必须保留：

- 导航、主要动作和互斥选择的必要名称。
- 无法从画面准确判断的保存、连接、权限、处理和发送状态。
- 错误原因、恢复方法、危险操作后果和不可逆确认。
- 用户作出正确选择所需的尺寸、范围、对象或版本信息。
- 关键状态的文字或结构化替代；不要只依赖颜色、图标或动效。

## 常见判例

- 图片已经显示背景被抠除，且“抠除背景”按钮处于选中态：删除“背景已抠除”标签。
- 同一发送百分比同时出现在标题、角标和进度条：只保留一个主进度表达。
- “已自动保存”无法从图纸内容看出，并影响用户是否安全离开：保留。
- 删除、覆盖或授权操作可能造成损失：保留明确的后果和恢复信息。

## 交付要求

- 修改前给出候选清单；修改后说明实际删除、缩短和有意保留的内容。
- 只报告真正完成的检查。工具调用成功不等于视觉或交互验收通过。
- 若完整审查后没有可安全删除的内容，明确报告已验证无需修改，不为制造变化而修改。
